# SPEC — функциональная спецификация CDXMonitor

Статус: проект, на согласовании. Основание: `docs/AUDIT.md`, `docs/METRICS.md`.

## 1. Цель и границы

CDXMonitor — локальное приложение (сервер + веб-UI) для отображения статистики Codex Desktop.
Открывается во встроенном браузере правой панели Codex по адресу `127.0.0.1:<порт>`.
Не расширение Codex, не патч, не прокси. Не зависит от OpenCode.

Не-цели: изменение сессий/логов/авторизации Codex; сбор текстов диалогов и секретов;
учет «всего аккаунта» без источника; выдуманные лимиты/сбросы/прогнозы без маркировки.

## 2. Функциональные требования

F1. Контекст: модель, effort, ID сессии, окно, занято/%, остаток, fresh, cache ratio,
Δ за событие, история заполнения, счетчик/время compaction, контекст после сжатия.
F2. Токены TURN / TASK / ROLLOUT: input, cached, cache-write, fresh, output, reasoning, total.
F3. Агрегаты: сессия, день, неделя, период; группировки по моделям и проектам (cwd).
F4. Лимиты: primary 5h и secondary weekly отдельно (расход %, обратный отсчет до `resets_at`),
`limit_name`/`limit_id`, credits-индикаторы, флаги spend-control. `plan_type` — только при наличии.
F5. Сессии: список всех primary-тредов (auxiliary с меткой и скрыты по умолчанию),
переключение сессии, суммарный вид; статусы turns и длительности (если подключен SQLite-адаптер).
F6. История: собственная SQLite-история наблюдений, выбор периода, графики (компактные, не на первом экране).
F7. Compaction-метр: число сжатий, время последнего, изменение контекста (из `compacted`-записей).
F8. Диагностика: состояние источников (файл/offset/скорость), счетчик неизвестных записей схемы,
ошибки парсинга, версия Codex, uptime монитора, last activity.
F9. Режимы UI: компактный (панель ~360 px, ключевые цифры без прокрутки) и расширенный (вкладки
Overview / Context / Tokens / Limits / Sessions / History / Diagnostics / Settings).
Оценочные (О) и недоступные данные маркируются в UI явно (бейджи `EST`, `N/A`).
F10. Демо-режим только на синтетике, включается флагом, визуально отделен (плашка DEMO).
F11. Стартовая boot-страница без сервера: файл `boot.html` (чистый HTML + inline JS/CSS,
без сборки и внешних CDN) открывается напрямую (в т.ч. по `file://`) при остановленном сервере;
показывает статус сервера и кнопку запуска; кнопка вызывает кастомный протокол `cdxmonitor://start`
(регистрируется install-скриптом в HKCU, без прав администратора); страница опрашивает
`http://127.0.0.1:<порт>/api/health` и при ответе 200 сама переходит (`location.replace`) на серверный UI.
Fallback: ручная команда запуска + продолжающийся опрос с автопереходом.
F12. Переносимая сборка `release/CDXMonitor/`: `web/` (статика UI без внешних CDN), `server/`
(сервер + зависимости), `config/` (настройки), `start.cmd`, `stop.cmd`, `install.ps1`,
`uninstall.ps1` (удаляет только файлы CDXMonitor), `README.md`. Изменяемые данные (история,
настройки) живут в отдельном `data/` вне статики; обновление сборки их не затирает.
В сборку попадает только необходимое (без исходников тестов и dev-зависимостей).
F13. Сервер сборки: default `http://127.0.0.1:8765`, порт настраивается (config + флаг `--port`);
занятый порт — явная ошибка и ненулевой exit, без молчаливого переключения. Показатели
обновляются автоматически (SSE), без ручной перезагрузки.
F14. Автообнаружение страниц: сервер находит `web/pages/*.html` при старте и отдает их по
`/pages/<имя>.html`; главная показывает переключатель; новые страницы появляются без правок
маршрутизатора. Защита: только basename `.html` внутри `web/pages` (realpath-проверка);
config/server/data не отдаются. Монитор остается SPA; отдельные HTML — только для новых
страниц, не для компонентов React.
F15. Интеграция Codex (без модификации Codex): действие Start CDXMonitor через официальный
механизм Local Environments → Actions (скрипт запуска сборки во встроенном терминале;
конфиг хранится в `.codex` проекта). Автозапуск при входе в Windows — опция, по умолчанию выключена.
Цели установки: `%LOCALAPPDATA%\OpenAI\Codex\CDXMonitor`, fallback `%LOCALAPPDATA%\CDXMonitor`;
окончательное расположение утверждает пользователь перед установкой; служебные файлы Codex
(bin, runtimes и др.) не трогаются.
F16. Идемпотентная установка: при наличии предыдущей версии обновляются файлы и конфигурация,
сохраняются настройки и `data/`; при отсутствии — новая конфигурация. Реестр установки —
собственный файл `.cdxmonitor-install.json` в корне установки (версия пакета, каталог, URL,
порт, тоглы автозапуска, метки времени); дубли записей исключены (один файл, обновление на месте);
запись атомарна (temp + rename), перед обновлением — резервная копия `.bak`. Имя не пересекается
с `config/cdxmonitor.json` (настройки сервера) и `.cdxmonitor-release.json` (маркер пакета).
F17. Два независимых тогла (оба — в реестре, default off): (а) автозапуск сервера при входе
в Windows; (б) автооткрытие вкладки — действует только через документированный механизм,
иначе сводится к готовой инструкции ручного открытия. Тоглы включаются только по запросу.

## 3. Требования к точности учета

- Идемпотентный реплей: рестарт/перечитывание не дублирует счетчики (семантика max-согласования из AUDIT §2).
- TASK-базлайн восстанавливается из файла (`total − last`), а не сбрасывается в ноль.
- `token_usage_record` первичен при наличии; `token_count` — fallback/согласование (компенсация compaction-usage).
- Reasoning может входить в output — показывать обе строки без двойного суммирования в total.
- Временные агрегаты строятся по `timestamp` событий, а не по времени наблюдения.

## 4. Надежность и безопасность

- Только чтение `.codex`; записи — лишь в собственную БД CDXMonitor.
- Белый список читаемых полей (METRICS §6); тексты диалогов и секреты не читаются и не логируются.
- Обработка: отсутствующие/битые строки, partial-EOF, ротация/усечение файла, параллельные сессии,
завершение/возобновление треда, смена схемы (счетчик unknown + предупреждение, изолированные адаптеры).
- Опрос: инкрементальный tail по offset; rescan новых файлов ≤ 1 раза в 5 c; UI-пуш по SSE.
- Bind по умолчанию `127.0.0.1`; graceful shutdown с освобождением watcher-ов.
- Файл 46+ МБ: стартовый реплей потоковый, без загрузки целиком в память UI.

## 5. Критерии приемки (сквозные)

A1. На живых данных показывает TURN/TASK/ROLLOUT, совпадающие с эталонным Python-монитором
(сверка на зафиксированном rollout вручную, допуск — точное совпадение целочисленных счетчиков).
A2. Оба лимита (5h + weekly) отображаются со значениями из `rate_limits`; при отсутствии — `N/A`, а не нули.
A3. Compaction: счетчик и время совпадают с числом `compacted`-записей в файле.
A4. Рестарт сервера не меняет ROLLOUT/TASK (идемпотентность).
A5. Неизвестная запись схемы не роняет коллектор и видна в Diagnostics.
A6. `tsc` без ошибок; smoke-тест этапов зеленный; синтетические unit-тесты коллектора зеленые.
A7. Страница открывается по `127.0.0.1` и помещается в узкую панель в компактном режиме
(проверка доступности из встроенного браузера Codex — отдельный пункт Этапа 2).
A8. `boot.html`, открытый из файла при выключенном сервере, показывает кнопку запуска;
после поднятия сервера страница сама переходит на UI без ручного обновления (кнопкой и fallback-режимом).
A9. Сборка ставится в чистый каталог и стартует двойным кликом `start.cmd` без среды разработки;
API и стартовая страница отвечают; статистика обновляется без перезагрузки.
A10. Обновление сборки поверх сохраняет `data/`; `uninstall.ps1` удаляет только файлы CDXMonitor
(контроль: служебные каталоги Codex целы).
A11. Новый файл в `web/pages/` появляется в переключателе после рестарта сервера;
запросы вне `web/pages` (обход директорий, config/server/data) отклоняются.
A12. Повторная установка поверх: `data/` и настройки целы, версия в реестре обновлена,
дублей записей нет, `.bak` создан. Установка в чистый каталог создает реестр с нуля.
A13. Тоглы автозапуска независимы; автооткрытие вкладки не заявляется без документированного
механизма и проверенной persistence (протокол проверки — в ARCHITECTURE §9).
